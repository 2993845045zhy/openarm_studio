# 左臂（can1）间歇掉线排查记录（2026-11-22）

> 现象：左臂 8 个轴同一瞬间全部不应答，之后主机侧 `write_no_buffer`（ENOBUFS）持续增长，直到重置 CAN 接口或重启。
> 右臂（can0）在同样的使用条件下几乎不出这个问题（日志里只有 2026-11-21 22:51 一次）。
> **状态：原因定位到"PCAN 适配器第 2 通道 ↔ 左臂"这条通路上，具体是适配器还是左臂线缆尚未区分**，见文末待办。
> 这是一台机器的现场排查记录，文中数字都是当时实测。

## 环境

- PCAN-USB Pro FD（单适配器双通道），`can0` = 右臂，`can1` = 左臂，CAN-FD 仲裁 1 M / 数据 5 M，内核 `peak_usb` 驱动
- Ubuntu 24.04，内核 7.0.0-43-generic；`restart-ms 0`（总线关闭后不自动恢复）
- 电机：达妙 DM8009×2、DM4340×2、DM4310×3 + 夹爪 DM4310；夹爪 `TIMEOUT` 寄存器为 0（失联后不会自己失能）
- 试验期间两臂电机全部失能，只发送状态查询帧，Studio 关闭

## 日志里看到的规律（`journalctl --user`，2026-11-21 至 11-22）

每次掉线的形态一致：8 个轴同时沉默 → 约 1 秒后主机开始 `write_no_buffer` → 之后每 5 秒 +160（空闲轮询退避到 4 次/秒 × 8 帧）。

| 重置接口后到掉线的时间（日志 + 当天试验） | 次数 |
| --- | --- |
| 5 s 以内 | 16 |
| 6–60 s | 9 |
| 60 s 以上 | 4（61–98 s） |
| 分钟级（两次，都只和夹爪单电机通信） | 7.5 分钟、10.8 分钟 |

`unmatched reply on id 0x7FF +7/+28` 是良性的：Studio 总线体检的 35 帧回显。

## 掉线之后发生了什么

- 适配器通道表现为"总线上一个节点都没有"：帧被主机接受，但电机收不到（掉线期间发的失能帧没有生效），也没有回包。
- 轻载下还能再接受约 225 帧，之后 `ENOBUFS`。Studio 以 200 帧/秒轮询时 1 秒多就填满。
- 等了 3 分钟和 16 分钟都没有自行恢复。
- 当天约 30 次试验里，每次重置接口后左臂都能立刻应答。Studio 日志里有两次例外（15:06:07、15:06:25），重置后没有恢复。
- 掉线期间左爪一直保持使能状态（16:22 那次），说明左臂电机没有掉电。

## 已排除

| 怀疑对象 | 依据 |
| --- | --- |
| 总线超负荷 | 按帧长估算：Studio 空闲时总线占用约 2–3%，使能后不超过约 10–15%；掉线时负载最低只有 8 帧/秒 |
| Studio 的代码或流量形态 | 不经 Studio、用最原始的查询帧照样掉 |
| 某一个电机 | 左臂 8 个电机逐个单独测都不掉 |
| 两条通道同时收发 | 右臂单独满载时左臂不掉；右臂在对压中从未掉 |
| 经典 / CAN-FD 帧型 | 两种都掉 |
| 纯时间触发 | 重置后空闲 10 s 不掉 |
| 电机掉电 | 掉线期间左爪保持使能 |

## 最符合全部现象的模型

左臂这条 CAN 通路会偶尔中断几毫秒。适配器如果在发送时撞上中断，就彻底停摆且不报任何错误
（它连"总线上没设备"都不报），只能靠重置接口救回。中断本身是线缆接触、终端电阻、地电位还是
适配器引起的，从主机这边分不出来。

内核 `peak_usb` 驱动里，发送上下文要等 USB 批量输出完成才释放；设备不再读取时上下文耗尽，
网卡发送队列停住，套接字写入就返回 `ENOBUFS`。

## 掉线时怎么办

1. 左臂处于使能状态时掉线，电机会一直执行最后一条指令，软件发的失能到不了它，只能拍急停。
2. Studio 里：先失能，再点「CAN 重连」；或关闭 Studio 后执行
   `sudo bash ~/openarm_studio/tools/can_reset.sh`。
3. 重置后若几秒内再次掉线，说明正处在发作期。

## 待办（需要现场操作）

1. **对调适配器上左右两条 D-Sub 线**，再给两条总线加同样的负载做对照：故障跟着线走到 can0 = 左臂线缆/供电侧；留在 can1 = 适配器通道。
2. **开启自动恢复和错误上报**（需要 root）：
   ```bash
   for i in can0 can1; do sudo ip link set $i down; sudo ip link set $i type can bitrate 1000000 sample-point 0.75 dbitrate 5000000 dsample-point 0.75 fd on restart-ms 200 berr-reporting on; sudo ip link set $i up; done
   ```
   之后监听 CAN 错误帧，看掉线瞬间有没有上报；若掉线变成 200 ms 的闪断，即证实上述模型。
3. `sudo dmesg | grep -i -E "pcan|peak"` 读出适配器固件版本。PEAK 官方驱动更新记录里，PCAN-USB Pro FD 硬件 4 版有 3.4.6 的固件门槛。

## 诊断脚本

排查时写了四个脚本：只读查询 16 个电机的状态和寄存器、发一串查询并统计回包与错误帧、每秒给两条总线各发查询以观察掉线后是否自行恢复、每轮重置接口后按指定负载加压并记录多久掉线。它们都只发状态查询帧，不会使能任何电机。脚本当时写在另一个工作区里，还没有整理进本仓库。
